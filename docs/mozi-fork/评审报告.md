## 0. 总评

方向正确，机制盘点质量高，但落地计划有 9 处承重前提经源码核验不成立。具体说：

- **Hermes 机制盘点（§1）是本文档最扎实的部分**：52 条断言 44 条完全证实、8 条细节偏差、0 条硬错。三个时间尺度、两段提示词精华、反迷信清单、curator 生命周期数字——几乎全部与源码逐字吻合。可以把 §1 当作可信的二手资料引用。
- **落地计划（§3）是薄弱部分**：9 条 S1 级前提错误，集中在同一类病——**把"需要新建的机制"当成了"现成可复用的机制"**（session-end 事件、子代理换 preset、origin 标记、schedule 触发、frontmatter 计量、fork 缓存收益）。每一条单独看都是"实现时再想办法"的小事，合起来意味着 Phase 2/3 的骨架要重画。
- **根本原因正是姊妹篇（字幕模块 v5）自己总结的教训**：`docs/mozi-fork/advices-for-v4.md` 的"测试先行不能代替事实先行 → Step 0 source verification"。本文档没有 Step 0，§2.1 能力矩阵与各 Phase 前提以事实口吻陈述而无逐条核验标记，结果四处承重前提核验即错。这是全文最重要的一个改进项（见 §8）。
- 值得保留的判断同样清晰：Phase 0 的排序与启用路径和仓内预留方案逐字吻合；"Model-visible ⟺ logged 是 DSH 结构优势"是全文最有价值的洞察；三角色缝纪律、预算强制整合、反迷信清单的移植判断都对。评审结论是**修订后可执行**，不是推倒。

## 2. S1：承重前提核验失败（动工前必须修订）

### S1-1 Phase 3 的默认触发点"会话结束"不存在，且 teardown 路径必然杀死复盘子代理

文档（:210）："触发：turn-end/session-end 事件挂插件（默认**会话结束**触发一次……）"。

源码事实：

- `SessionEventMap` 没有 session/end。唯一形似的 `'session/end-seed'` 被定义为构造期种子边界标记，"NOT a liveness signal about other writers"（`packages/core/session/src/types.ts:303-324`；词表全文 `packages/core/session/src/known-event-types.ts:46-66`）。
- `session/disposed` 是 teardown 事件：CLI 进程退出的优雅期是 **5 秒**（`apps/cli/src/process-shutdown.ts:4` `PROCESS_SHUTDOWN_TIMEOUT_MS = 5_000`，:54 在每次 shutdown 启动时即布防）；headless 运行结束即 `io.exit`（`packages/bundle/headless/src/index.ts:198-204`）。
- `session/disposed` 的监听是 contained fire-and-forget，**返回值不被等待**（`packages/core/session/src/index.ts:1000-1001`、:388-394）——监听器无法暂停 dispose 来等复盘跑完。
- 子代理死于 owning fiber 的 unwind（`packages/subagent/subagent-in-process-driver/src/index.ts:223-224`："Disposal can tear the owner down before the loop records its ordinary `aborted` end"）；整个 subagent fiber dispose 时由 continuation manager 的无范围 `drain()` 收尾（`packages/subagent/subagent/src/continuation.ts:388-391`）。
- `Agent.runMaintenance`（`packages/core/agent-loop/src/agent.ts:149`）确实是 idle 相位的等待槽（compaction-basic 与 schedule 在用），但它同样在 5 秒窗口之内，`appExit` 契约上就是 "bounded"（`packages/boot/cmdline/src/index.ts:35`）。

**对抗复核结论：成立。** 在 session/disposed 上触发 LLM 复盘在 headless 与常驻宿主下都无法跑完。

**处方**（三选一并写明"谁保证复盘跑完"）：

(a) 长驻宿主（web/gateway）用 `turn/end` + 空闲去抖触发（`agent/turn-stopping` 或 `session/event` 观察，配 Config 阈值）；

(b) **"下次 resume 时复盘上一个会话的日志"**——学习滞后一步，但零 teardown 竞争、天然幂等、可用现有 durable 状态去抖，最贴合 DSH 的会话可恢复常态；

(c) headless 一次性进程在最终 `turn/end` 后、exit 前同步 await——这需要挂进应用退出序列（boot/app 接线），是新机制而非插件可自带。

### S1-2 "子代理 preset 按域组合"不是 DSH 的子代理组合机制

文档（:204）："子代理 preset（复用 `packages/preset/` 按域组合，只挂 memory + skill-manage + session-query 读工具）"。

源码事实：子代理创建时 **join 父亲的 live preset**（`packages/subagent/subagent/src/child-agent.ts:204` `composeFrom(childCtx, parent.ctx)`；`packages/preset/agent-presets/src/index.ts:446-458`），每孩子只有 `ChildComposition { persona?, toolFilter? }` 两个旋钮（`child-agent.ts:158-163`）；`SubagentStartRequest` 没有 preset 概念（`packages/subagent/subagent/src/types.ts:101-157`）。且 toolFilter 只能减不能增："a per-child restriction intersects with everything its chain admits"——父组合没挂 memory/skill-manage，复盘孩子就无从用起。另注意 `SubagentCapabilities`（`types.ts:88-92`）确认 toolFilter/persona 是仅有的两个受限面。

**处方**：(a) 复盘子代理 = 父 preset 之子 + `toolFilter.allow` 收窄（前提：基础组合显式装配 memory+skill-manage——这是一个新的基础组合决策，要写明）；(b) 放弃子代理映射，由插件在常驻进程组合带 curator 式组合的根会话（webhook 创建根会话是先例，`packages/webhook/README.md`）。

### S1-3 Phase 3 的 fork KV-cache 收益被它自己的白名单机制摧毁

文档（:203）宣称"fork 型还保 KV cache"，同段（:204）又要求复盘子代理只挂三个工具。两者不相容：

- fork 前缀复用要求子与父 system prompt + tools[] **字节一致**，"reuse stops at the first differing byte"（`.agents/notes/implemented/architecture/2026-08-10-fork-children-stay-one-shot.md:9`；`packages/subagent/subagent-fork-in-process/README.md:122` "Persona, tool-filter, generated-SDK, or route changes may invalidate reuse"）。
- DSH 的 toolFilter 是一元可见性："the named tools vanish from the child's prompt AND refuse to execute (one visibility)"（`packages/subagent/subagent/src/types.ts:142-148`）——没有 Hermes 式"可见但运行时拒绝"模式。Hermes 的 ~26% 节省恰恰靠保留完整 tools[] 字节一致 + 运行时拒绝（`mozi-hermes-agent/agent/background_review.py:1318-1320`，"keeps tools[] byte-identical to the parent so its outbound request hits the same provider cache prefix"）。
- 仓里已有 TODO 与 issue 记录这个坑：`TODO(fork-continuable-prefix-reuse)`（`subagent-fork-in-process/src/index.ts:84-89`，issue #2124）；base bundle 特意把 fork 固定 one-shot 保前缀（`packages/bundle/base/cordis.patch.yml:362-373`），CLI preset 则保留 continuable 并明确接受前缀损失（`packages/preset/agent-presets/presets/standard/agent.cordis.yml:198-205`）。
- `tools.guard()`（`packages/core/tools/src/index.ts:1100-1109`）理论上可复现 Hermes 模式，但它不在委派缝内、且与仓库既有的 scope-local authority 裁定相抵触——不能当作现成能力引用。

**对抗复核结论：完全成立**（精确化：one-shot fork 在字节一致时确实复用前缀，失效仅由 toolFilter/persona delta 引起；capability matrix :146 对"未配置 fork"的表述本身没错，错的是 Phase 3 的组合使用）。

**处方**：二选一并写明代价——(a) 冷缓存：toolFilter 窄化（现成能力），放弃热前缀，用 `agentOptions` 把复盘路由到廉价模型补成本；(b) 热缓存：fork 不带 persona/toolFilter（与父字节一致），白名单改为子代理作用域内的运行时执行拒绝（需新机制，Hermes 模式）。

### S1-4 `SessionHeader.origin = 'self-review'` 写不进去，且扩它是双向破坏

文档（:155、:205）："SessionHeader 已有 origin、agentPreset 字段——复盘子会话可以干净地标记来源" / "SessionHeader.origin 标记 self-review"。

源码事实：

- origin 是单成员闭联合集：`readonly origin?: 'subagent'`（`packages/core/session/src/types.ts:85`），创建时校验直接抛错（`packages/core/session/src/index.ts:125-127`），写入方硬编码（`packages/subagent/subagent/src/child-agent.ts:151`），**两个持久化后端的 schema 都锁死该值**（`packages/session/session-persistence-sqlite/src/schema.ts:30` `'subagent' | null`；jsonl format 谓词），还镜像进生成的 api-catalog（`packages/extensions/tool-cordis/src/api-catalog.ts:4887`）。
- 扩为 `'subagent' | 'self-review'` 的消费面清单比文档想象的长：list-children 判据（`packages/subagent/subagent/src/list-children.ts:88-89`、:187、:273）、`control-types.ts:25-26`、ACP resume、api/session-controller（6 处）、两个 client UI 包、tool-subagent 的模型选择继承。
- **对抗复核的两点修正**：(1) teardown 排空**不**按 origin 过滤（drain 走 runtime ancestry，`continuation.ts:770-778`），原文档评审稿里"会被排空剔除"的说法不成立，撤回；(2) 反向破坏是真的——新值会被 ACP 当作可恢复的顶层会话、在 client 会话树里显示为普通会话。另外 `listDescendants` 会**穿过**非 'subagent' 节点继续遍历（`list-children.ts:274-277`），按 id 直接续聊也不受影响（授权走 `parentSession` + descriptor mode，`continuation.ts:975,984`）——破坏面是**枚举/发现**，不是续聊能力。

**处方**：便宜路线是用已有的自由字段承载溯源：`agentPreset`（自由字符串，且已入 sqlite 索引列，`packages/session-query/session-query-sqlite/src/index.ts:163-172`）或子代理 descriptor 的 label/mode。若坚持扩 origin，把"union 扩容 + 校验 + 双后端 schema + api-catalog 再生 + 全部读取点 + 双 SDK expected outputs"列为 Phase 3 显式交付物。

### S1-5 计量计数器内联 frontmatter 且"加载时递增"：把读路径变成写路径，五处连坏

文档（:180）："新增 created_by: agent 与计量元数据（use_count / view_count / patch_count / last_used_at / state / pinned……内联进 `metadata`）；`skill` 工具加载时递增计数"。

源码事实（每条独立成立）：

1. **沙箱**：走 `ctx.fs` 时，workspace-write 的可写根只有 workspaceRoot+/tmp（`packages/sandbox/sandbox/src/roots.ts:52-55`），`~/.dsh/skills` 不在其中 → `FS_SANDBOX_DENIED`（`packages/fs/fs-sandbox/src/index.ts:140-141`）；read-only 档全拒（:126-127）；未获批准的拒绝可按调用升级，但那意味着**每次技能加载弹一次审批**。cwd 在仓库子目录时更糟：`findProjectRoot` 向上找 `.git`（`skill-filesystem/src/index.ts:937-947`），projectRoot 是 workspaceRoot(=cwd) 的祖先，`<projectRoot>/.dsh/skills` 写入同样被拒。
2. **绕开沙箱**（裸 node:fs，如 `session-persistence-jsonl` 写 `~/.dsh/sessions` 的先例，`packages/session/session-persistence-jsonl/src/index.ts:552-556`）运行时无人拦截，但文档自己声称的"同步失效红利"就没了：`fs/observed` 的同步失效只认 `edit`/`write` 两个 actor（`skill-filesystem/src/index.ts:139-142`、:693-697），见 S2-3。
3. **git 污染**：`.gitignore` 只忽略 `.dsh-build/`（.gitignore:35），项目域每次加载都弄脏用户工作树、可被顺手提交。
4. **并发互踩**：多会话读-改-写同一 SKILL.md 丢更新；且计数器变化使 Phase 1 自己的读后才写守卫失效（守卫比对加载原文摘要，计数器一变摘要即变）。
5. **Hermes 的对照组**：账本放技能文件外的 `.usage.json` sidecar（`tools/skill_usage.py:3`），并配跨进程文件锁（`tools/memory_tool.py` 同族；`skill_usage.py:90-122` 有自己的锁）——文档 §1.3 自己引用了这一点，§3 却选了内联。

**对抗复核精确化**：拒绝路径并非绝对不可行（有 per-call 审批升级，`packages/fs/tool-fs/src/write.ts:106-116`；裸 fs 通道也无运行时拦截），所以定性是"**文档必须指定写通道**（ctx.fs 还是宿主自有持久化）并为 dshHome 给出策略供给或显式豁免"，而非"证明不可行"。但"每次加载写文件"在任何通道下都是错的。

**处方**：计量走 sidecar（`ctx.storageDomain` KV 已在 base bundle 挂载且 message-feedback 已用它，`packages/storage/storage-domain/README.md:11`；或 `$DSH_HOME` 账本文件 + 锁）；`skill` 加载保持纯读；frontmatter 只留 created_by 等低频作者字段。

### S1-6 技能所有权/遮蔽治理缺失：agent 写 rank-100 会遮蔽仓内人工策展技能，且与仓内既有人审提案正面冲突

源码事实：

- "Lower ranks win duplicate skill names before provider registration order is considered"（`packages/skill/skill/src/index.ts:75`）；`.dsh/skills`=100 < `.agents/skills`=200（`skill-filesystem/src/index.ts:36-40`），本仓 `.agents/skills/` 下有 10 个人工维护技能。agent 创建同名技能即静默遮蔽维护者内容；patch 一个 winning candidate 来自 rank-200 时写到哪里，文档没有答案。注册表没有任何可写性/所有权概念（`skill/src/index.ts:38-39` "prompt-visible metadata, not precedence by itself"）。
- Hermes 对此的回答是**运行时强制**的：`_background_review_write_guard` 逐类拒绝 pinned/external/bundled/hub/非 curator-managed（`tools/skill_manager_tool.py:335-455`，缺记录时 fail-closed，#67140；"Run `hermes curator adopt {name}` to opt it in"）。文档 §1.4 总结了这个边界，§3 却没有导入。
- 仓内既有提案 `.agents/notes/proposed/process/2026-07-13-human-review-skill-maintenance.md` 明确记录了方向性拒绝："**Create or merge repository changes automatically** — rejected"，要求双人独立评审 + adoption evidence 才允许技能变更落地。文档 :134/:266 只把它当"无自动创建能力"的库存证据引用，未回应其结论。

**处方**：(1) 可写 source 白名单 + patch 目标解析规则写死（拒绝 patch 非 project-dsh 胜者，或写遮蔽副本并在结果中明示）；(2) 新建技能默认 `state: draft` 不进模型目录（复用 frontmatter 的 `disable-model-invocation`），由用户提升；(3) 后台复盘 fork 的写面收窄到 `created_by=agent` 条目（为 Phase 3 铺路）；(4) 加一节"与 human-review-skill-maintenance 提案的关系"：领地划分（模型自治域 vs `.agents/skills` 人工域）+ 把该提案的 adoption-evidence/双人评审作为"提权进人工域"的通道。

### S1-7 复盘提示词把"用户纠正/不满"当一等信号，与 feedback 隔离政策正面冲突，输入契约未声明

源码事实：`packages/feedback/README.md:11` "Neither kind of feedback reaches the model — these are signals about the output, never input to it"；:22 session remark 还参与 sharing-gated 同意流。移植的复盘提示词（文档 :87、:212）把"用户纠正/不满"列为一等学习信号，但没说复盘从哪里取"纠正"。

**处方**：Phase 3 加一句输入契约——复盘唯一输入是会话日志中的普通 user message（transcript 内的用户纠正）；feedback 存储（messageFeedback/command-feedback）对模型侧读者保持不可见；未来若要把评分纳入学习信号，先修 feedback 政策文档，不许默默打通。

### S1-8 复盘子会话持久化后被 FTS 索引：复盘提示词经检索回流未来会话

文档（:246）的对策只堵了主会话日志这扇门："复盘子会话独立持久化，其 prompt 绝不进入主会话日志"。但复盘子会话本身落在同一 session store，而 session-query 对**全部**持久会话建索引（索引列含 delegation_depth，无 origin 排除，`packages/session-query/session-query-sqlite/src/index.ts:577`；搜索默认全量，:639-666）——复盘的提示词、"没什么可学"的自言自语、被否决的写入草稿都会成为未来会话可检索的语料。这正是 Hermes `_persist_disabled`（`background_review.py:1341`，curator 接管事故的防线上半段）要防的泄漏类，从 FTS 这扇门又回来了。

**处方**三选一：(a) 复盘子会话不落盘（进程内临时存储，完全对齐 Hermes）；(b) 落盘但 session-query 索引按来源排除（需要索引 schema 变更——origin 目前甚至不在索引列里）；(c) 接受回流并把复盘提示词写成可检索的免毒内容。若 Phase 0 先开了内容搜索，这个决策就必须在 Phase 3 之前做。

### S1-9 Phase 4 的 curator 触发是类别错误：schedule 是会话内投递，"宿主空闲钩子"不存在

文档（:216）："触发可借 `packages/schedule/` 或宿主空闲钩子"。

源码事实：schedule 的合同是把到期提醒作为消息送回**同一条活会话**——"If the session is closed or cold when a reminder comes due, it stays overdue until a future live root agent resumes the session — nothing is sent outside the session"（`packages/schedule/schedule/README.md`）；它表达不了"宿主空闲 ≥2h 且无会话活动时跑整理"。"宿主空闲钩子"在仓里没有对应物：`AgentStatus` 只有 'idle' | 'running'（agent 级，每回合后都会进入，`packages/core/agent/src/runtime-types.ts:53`）；`ctx.jobs` 是"belong to the agent session that started them"（`packages/jobs/README.md:11`）。而周级 curator 必须有驻留进程——按仓规 "Only `dsh` profiles launch supported Node apps"，这是 app/profile 层交付。

（对照 Hermes：它的 curator 实际上也只在 CLI 启动/网关 tick 检查，且两个接线点都传 `idle_for_seconds=float("inf")`——2 小时空闲门在现网是死代码，见 §4-6。）

## 6. 经对抗复核确认的优点（修订时应保持）

1. **Phase 0 选得准且启用路径与仓内预留逐字吻合**：五工具确已实现且未进任何 shipped bundle（唯一组合是 spill 场景的 snapshot patch），`openAt: never` + `:memory:` + 后层覆盖的注释（`cordis.patch.yml:120-133`）就是文档 Phase 0 的原话；工具本身质量过硬——caller 工作域授权（cwd 精确匹配）、`capped` 截断语义、现成 presentCall。
2. **技能缝结构红利的判断正确**：watch + 首方写直通失效 + digest 驱动的目录重发布 + 缺失根探测（README:79 "a root that does not exist yet is probed until it appears"）——"agent 写技能 → 下一步自动入目录"的闭环机制真实存在（只是对"新工具"需要 S2-3 的接线）。
3. **三角色缝纪律**：Phase 1/2 坚持补 Consumer/Service Definition/Provider 而非孤立工具，与 `docs/glossary.md:9`、`architecture.md:111` 完全同构。
4. **预算强制整合整体移植**：超预算拒绝附全量条目 + 本回合配方 + 连败终态 + 成功不回显——这是 Hermes 用生产事故（#42405）换来的"学习写入不得饿死主回复"机制，文档连"做成 Config 字段"都对。
5. **反迷信清单 + 更新优先序 + "没什么可学是正常结局"**：全文档迁移价值最高的判断；把 Hermes 的"要积极"（原文是 "Be ACTIVE"，:476-480）写入偏置用触发频率与终局设计对冲，方向正确。
6. **"curator 接管"的结构性预防**：复盘子代理是独立耐久会话，复盘 prompt 物理上进不了主会话日志——Hermes 靠 `_persist_disabled` 一堆运行时开关防的事故，在 DSH 是构造性不可能（子代理还会自动拒绝需审批的操作，`child-agent.ts`）。唯一的残缺口是 FTS 回流（S1-8），堵上即完整。
7. **Model-visible ⟺ logged 被识别为 DSH 结构优势**——全文最有价值的架构洞察，且经对抗复核后**比文档声称的更强**：连 system prompt 的完整字节都逐字进日志并被不变量强制（`invariant.ts:45`），学习产物的溯源与可回放是白送的。
8. **curator 后置 + LLM 整合默认关 + 质量门作为反超点**：排序吸收了 Hermes 真实的教训（consolidate 默认关、成本争议）；质量门（Verification 章节 + draft→active）直击其"学到的技能无效力验证"，与 DSH gate 文化及 2026-07-13 提案的人审精神相容（关系陈述见 S1-6 处方 4）。
