# 第九轮评审建议：RC5.5 自我进化机制（证据复核修订版）

> 初评与复核日期：2026-09-01；DeepSeek Harness 基线：`16bd8323def3178fb6c21e008e9e2c28d2458896`；mozi-hermes-agent 基线：`05c248d8a6c7f6d0d26efbb35fba3d6dfeb36a06`；范围：RC5.5 方案、函数级规格、P0–P4 附件、执行进度、直接相关 DSH 源码与 Evidence Lock，以及 Hermes 的 background review、memory、write approval、skill authoring、usage/curator 源码与文档。

## 摘要

RC5.5 的主架构仍然值得继续：模型只提案、Host 提交；计划先持久化；memory/skill 使用资源级 receipt；skill draft/pending 与模型可见版本分离；跨资源失败采用 forward recovery。这些设计比 Hermes 直接让 background agent 调用 memory/skill 工具更容易证明幂等、隔离和恢复，应保留。

证据复核后，本评审撤回两项原 S0/S1 判断并修正三项措辞。`OpId` 不存在已证明的自引用：Evidence Lock 已在计划层实现独立的 `canonicalOpDigest(op: unknown)`，而 P1 memory 中的同名函数是 Host op 的结果摘要。`reviewProvider` 是子代理执行后端，不是 LLM 服务商；现行 P3 只覆盖继承父 provider 后可选 model，因此原“RC5.5 已允许跨 LLM provider 泄露”的判断没有依据。Hermes write approval 也不是默认行为，而是默认关闭的 opt-in 开关。

修正后仍有三个 S0 阻断项：前台 `skill_manage` 没有定义权威 `OpId` 与 receipt 终结者；review planner 的无工具隔离和 root-only/non-recursive 条件没有进入最新函数规格；finalization 在 `markFinalized` 与 cursor release 之间存在未覆盖的崩溃状态。另有多项 S1 缺口会使系统稳定地保存错误经验、反复重试、发布旧 memory，或根本无法批量处理冷历史会话。

最终建议不是停止 P1，而是按依赖点收紧开工门：P1 Service/Publisher 可以继续，但必须闭合存储预算与发布预算，并约束 scanner 覆盖；P2 mutation path 在前台工具操作身份闭合前不得完成；P3 planner/saga 在隔离、目标定位、outcome admission、retry 和 finalization 修正前不得完成；Conservative L1 必须执行总纲已经提出但尚未具体化的 quality harness 与人工升级 gate。

## 三、按严重程度展开

### 1. S0：前台 `skill_manage` 缺少操作身份与 receipt 生命周期

**证据。** `RC5.5-附件P2-skill-managed.md:75-79` 的 `createDraft/patchDraft` 必须接收 `requestedBy: OpId`，revision 和 receipt 都依赖它；同附件 `:90-93` 的工具规格只写 cwd/scope 与 action，没有说明 `requestedBy`。P2 又先于定义 ReviewAttempt 的 P3，不能调用 P3 专属 `deriveOpId`。所有新 skill receipt 先进入 `pendingReceipts`，但 `acknowledgeTerminalOps` 的唯一调用者被写成 P3 finalization；普通前台工具调用不属于 ReviewAttempt，因此没有 terminal ack owner。

DSH 已经提供可用的 Host 身份：`ToolRunContext` 携 branded `callId` 和当前 `agent`，见 `packages/core/tools/src/index.ts:315-339,380-405`；session id 可从 agent 的 durable header 取得。缺口不是基础设施不存在，而是 P2 规格没有使用它。

**影响。** 任意实现都只能在模型参数、随机 ID、P3 类型依赖和无界 pending receipt 之间自行选择；这些选择具有不同恢复语义，不能靠实现者猜测。

**修正。** 在 P2 定义 `DirectToolOperationOrigin {sessionId, callId}`，并由 Host 派生 `OpId = hash(domain, sessionId, callId, canonicalToolArguments)`。review op 继续由 attempt/index/plan digest 派生。直接工具写入没有跨资源 saga，receipt 应在同一资源提交中直接进入 bounded terminal ring；review 写入才先进入 pending、由 attempt terminal ack。若工具执行可能由 durable call 重放，必须用同一 session/call id 命中 duplicate。

**验收。** `tool-op-id-derived-from-session-and-call`、`tool-op-id-not-model-supplied`、`foreground-skill-receipt-enters-terminal-ring`、`foreground-receipts-remain-bounded`、`same-tool-call-retry-does-not-create-second-revision`、`p2-does-not-import-session-review`。

### 2. S0：planner 隔离和非递归条件在最新函数规格中缺席

**证据。** `RC5-外部建议核验与处置.md:69` 已接受 review child 使用 `toolFilter.allow: []` 与 output schema，只产生 proposal。P0 T02 证明空 allow-list 能隐藏并拒绝全部工具。最新 `RC5.5-附件P3-session-review.md:82-84` 却没有把 toolFilter 写入 `startPlanner` 请求和验收。

`packages/subagent/subagent/src/child-agent.ts:177-210` 显示 in-process child 会加入父 preset，然后只用 persona/toolFilter 做子 scope 覆盖；`packages/subagent/subagent-spawn-in-process/src/index.ts:49-50` 同时说明它不继承父 conversation。准确结论是：child 没有父对话历史，但会继承父的工具和 standing prompt composition。P3 `:123` 已把 standing prompt 继承列为 Known Limitation。若不显式 `allow: []`，authoring preset 中的 `skill_manage` 可达，planner 就可能绕过 stored plan、whole-plan admission 和 saga。

另一个未冻结条件是触发对象。child header 明确写入 `origin:'subagent'`（`child-agent.ts:138-155`），但 P3 的 `maybeDispatch/onForegroundTurn` 没有 root-only predicate。session-review 本身挂 authoring preset；没有测试证明 review child 的 turn/end 不会再次触发 review。

**修正。** 首选使用一次性、无工具的 planner provider，而不是完整 Agent。若继续使用 spawn child，`startPlanner` 必须固定 `toolFilter:{allow:[]}`，并测试 child request 只含显式 LearningView/persona 加不可避免的宿主 standing sections。trigger 必须拒绝 `header.parentSession`、`origin:'subagent'` 或非零 delegationDepth；Host mutation service 也不得接受 review actor 通过模型工具直写。

**验收。** `planner-tool-list-is-empty`、`planner-tool-execution-is-denied`、`planner-has-no-parent-conversation-history`、`planner-standing-context-is-explicitly-snapshotted`、`no-resource-write-before-plan-persisted`、`review-trigger-root-session-only`、`review-child-turn-end-never-dispatches-review`。这些断言必须走真实 authoring preset boot。

### 3. S0：finalization 的最后一个崩溃状态未被覆盖

**证据。** `RC5.5-附件P3-session-review.md:63` 说先清 inFlight 再 `markFinalized`，`:77` 说先 `markFinalized` 再 release，`:79` 又恢复为先清再 mark。参考实现 `packages/review/session-review/tests/evidence-lock/review-protocol.ts:769-816` 采用 ack→advance→markFinalized→release。T67 在 `finalization.spec.ts:304-348` 只注入 after-terminal、after-ack、after-advance，没有 after-finalized。若进程在 mark 与 release 之间崩溃，`recoverTerminal()` 不再扫描该 finalized attempt，而 cursor `recover()` 会把非 planning 的 occupied attempt 当 resumable（`review-protocol.ts:237-251`）。

**修正。** 不应简单交换最后两步，因为 release 后、mark 前也可能让同进程新 claim 与旧 terminal attempt 并行。最小修法是把 `finalized` 定义为“receipt/high-water 等不可逆义务完成”，cursor release 定义为可重建清理：继续执行 markFinalized→release；claim/recover 遇到 occupied attempt 时查询 ledger，若已 finalized 就先幂等 release，绝不能返回 resumable。启动时先完成 `unfinalized terminal` 与 `finalized + occupied` 两类 reconciliation，再接受新 review mutation。若不希望跨表查询，则必须把 finalization phase 与 cursor 占用合并到一个权威记录中。

**验收。** `crash-after-finalized-before-release-recovers`、`finalized-occupied-is-released-not-resumed`、`startup-reconciles-before-new-claim`、`unfinalized-terminal-replays-obligations`、`finalization-crash-injected-after-every-durable-write`。

### 4. S1：memory update/remove 没有权威目标

**证据。** `自我进化机制-RC5.5-方案.md:97-102` 的 memory plan 只有 `targetHint?`；`HostMemoryOp` 却要求精确 `entryId`，见 `packages/memory/memory/src/types.ts:73-83`。`foldMemoryOps` 对未知 update/remove 失败，见 `packages/memory/memory/src/fold.ts:160-180`。没有函数把 hint 无歧义地解析成当前 entry，也没有 stale target 验收。

Hermes `tools/memory_tool.py:473-584` 使用 `old_text`，并对零匹配或多匹配失败。这比静默猜测好，但 DSH 已拥有 branded ID，应采用更强的定位方式，而不是复制 substring API。

**修正。** ReviewPlan 使用判别联合：add 带 content；update/remove 必须带 `targetEntryId` 和 `expectedEntryDigest`，update 再带新内容。currentMemory 输入向 planner 暴露 opaque ID/digest；Host 精确 CAS。`targetHint` 可以作为非权威说明，不能参与选择记录。

**验收。** `memory-update-targets-exact-entry-id`、`memory-remove-targets-exact-entry-id`、`memory-target-stale-digest-zero-commit`、`memory-target-unknown-zero-commit`、`memory-plan-duplicate-target-zero-commit`。

### 5. S1：evidence admission 没有证明经验有效

**证据。** `RC5.5-附件P3-session-review.md:37-39` 只验证 seq、span、来源种类和上限；`observed-project` 要求 tool outcome，但失败 tool result 同样是 outcome。DSH 的 completed turn 只表示没有后续 tool call 或工具声明结束，见 `packages/core/agent-loop/src/agent.ts:426-434`，不代表用户目标成功。当前规格没有 Host-derived success、用户纠正、失败→修复→验证或 unresolved 分类。

Hermes 已经从实际使用中记录了这一风险：`agent/background_review.py:580-612,693-724` 禁止把缺少二进制、未配置凭据、短暂错误、工具负面断言和没有找到工作方法的 unresolved failure 固化成 skill；重试成功时只保存 retry/fix pattern。Hermes 主要依赖 prompt，DSH 应将核心规则提升为 admission。

**修正。** LearningView 投影同时产生 Host-derived `OutcomeEvidence`：显式用户纠正、工具成功及验证产物、失败后修复并成功、未解决失败、瞬态环境错误、未知。procedure/skill proposal 必须引用成功 outcome 或完整的 failure→fix→verification 链；assistant 自称成功不能单独成立。未解决失败可以进 review ledger 供评估，但不能进入模型可见 memory/skill。

**验收。** `unresolved-failure-produces-zero-visible-learning`、`missing-binary-is-not-durable-rule`、`assistant-success-claim-is-insufficient`、`failure-fix-verification-saves-only-working-path`、`explicit-user-correction-is-admissible`、`transient-retry-saves-retry-pattern-not-failure`。

### 6. S1：计划摘要已有参考实现，但生产归属、版本和操作顺序未冻结

**证据。** P0 reference 的 `canonicalJson/canonicalOpDigest/deriveOpId` 是无环且可工作的，见 `review-protocol.ts:20-63`。但 P3 模块布局没有 canonicalization 模块，`deriveOpId` 只接收一个未定义来源的 `canonicalOpDigest` 参数。真实 ReviewPlan 在 `自我进化机制-RC5.5-方案.md:97-102` 分成 memory[] 和 skills[]，而 T62 reference 使用一个预先展平的 PlanOp[]；`stableOpIndex` 是全 plan、每资源数组还是按 commit 顺序编号没有规格。P1 又导出同名 `canonicalOpDigest(HostMemoryOp)`，语义是 result digest，不是计划摘要。

**影响。** 两个正确但不同的实现都可能通过各自单测，却给同一 stored plan 派生不同 op id；升级 canonicalization 后恢复旧 planned attempt 也可能改变身份。这里的问题是协议归属和版本，不是自引用。

**修正。** P3 明确定义 `enumeratePlanOps(plan)` 和 `canonicalPlanOpDigest(op, identityVersion)`；固定 memory/skill 跨数组顺序、数组内顺序、undefined、Unicode 与对象键规则，并将 identity version 随 attempt 持久化或纳入 attempt id。P1 的函数改名为 `memoryResultDigest`，避免实现者误接。把 P0 向量复制为生产包验收数据，但不要 import test-tree reference。

**验收。** `review-plan-enumeration-order-pinned`、`canonical-plan-digest-vectors-match-evidence-lock`、`canonical-plan-digest-excludes-host-fields`、`identity-version-survives-planned-recovery`、`memory-result-digest-not-used-for-op-identity`。

### 7. S1：retry、backoff、attempt cap 和 manual 没有闭合到 claim

**证据。** P3 `ReviewAttempt` 有 attemptCount/nextRetryAt，Config 有 `maxAttemptsPerRange/retryBackoffBaseMs`，`markTerminal` 也描述 retryable 背退；但 `ReviewCursorStore.claim()` 的函数规格没有 now、ledger retry state 或 blockedUntil 输入。T68 `finalization.spec.ts:387-418` 在 retryable/manual finalization 后立即再次 claim，并期望 acquired。T68 钉住“不推进”，没有钉住“何时允许重领”，因此与 backoff 描述并不等价。

**修正。** 明确谁拥有 due 判断。可以让 scheduler 在调用 cursor 前查询 durable range state，也可以把 `claim(sessionId, desiredThrough, now)` 与 latest disposition 放进同一 review-domain RMW；两种方案只能选一个并写出竞态语义。retryable 在 blockedUntil 前不得 spawn，达到 cap 后进入 manual hold；manual 必须由治理 release/skip，不能在下一 turn 自动重领。superseded 可立即重规，但仍受 consolidation/stale replan 上限。确定性 admission 拒绝仍可按现有“不跳过 evidence”原则重审，但必须背退，不能 tight loop。

**验收。** `retry-not-claimable-before-blocked-until`、`retry-claimable-at-blocked-until`、`retry-backoff-survives-restart`、`retry-stops-at-exact-attempt-cap`、`manual-hold-requires-governance-release`、`superseded-replan-respects-own-cap`。

### 8. S1：memory admission 与 publication 预算不闭合

**证据。** `packages/memory/memory/src/fold.ts:90-105` 只检查 maxEntries/maxStoredChars/maxEntryChars；`:300-325` 的 composite renderer 另按 maxSnapshotTokens 拒绝。`MemoryConfig` 将这些值独立配置，见 `types.ts:155-168`。P1 publisher 对所有异常 fail-open，因此某个成功提交且稳定超 publication budget 的状态会反复保留旧 snapshot。

**修正。** Config load 时证明最坏可见状态可发布，或在资源 RMW 提交前对 candidate composite 做确定性 preflight。L1 只有 project scope，也必须计入 header、ID、围栏和 blocked placeholder；L2 再把两 scope 总和纳入。publisher 的瞬态读错可以 fail-open，确定性 budget mismatch 应作为配置/先前 admission 错误告警，不能长期伪装成正常降级。

**验收。** `every-admitted-memory-state-is-publishable`、`snapshot-budget-includes-render-overhead`、`composite-budget-includes-all-enabled-scopes`、`invalid-memory-budget-combination-fails-load`、`deterministic-publication-failure-surfaces-invariant`。

### 9. S1：当前方案没有批量处理冷历史会话

**证据。** P3 cursor 是 per-session，触发来自当前 Agent 的 resume、first request 和 turn/end。`maintenance` 只是触发模式；没有 session 枚举器、跨 session queue/checkpoint、批量成本上限或测试。没有再次打开的旧 session 不会产生 Agent lifecycle 事件。

Hermes 的 `session_search` 提供 SQLite/FTS5 历史检索，见 `website/docs/user-guide/features/memory.md:185-211`；它是按需召回，不是自动提炼。Hermes background review 也主要处理当前 conversation snapshot。两个事实都不能替代 DSH 的历史批处理设计。

**修正。** 如果产品目标只是“新会话和被恢复会话”，文档应明确缩小承诺。如果目标确实是用户要求的“从历史会话提炼”，增加 `HistoricalReviewCoordinator`：枚举授权范围内的 root sessions，使用 durable global checkpoint/queue，限定项目、时间、速率和 token，并与实时 review 共用 per-session claim。

**验收。** `maintenance-discovers-cold-root-sessions`、`maintenance-excludes-child-sessions`、`maintenance-checkpoint-survives-restart`、`maintenance-and-live-review-do-not-double-claim`、`maintenance-honors-project-time-and-rate-limits`、`maintenance-opt-out-stops-new-claims`。

### 10. S1：L1 memory 缺少纠错治理，但不必强制所有写入审批

**证据。** RC5.5 为 skill 定义 draft/pending、approve/reject/reopen；L1 project memory 则直接 commit 并在下一个 pre-step 发布，没有 memory list/show/correct/remove 命令。方案 `:147,157` 已把 PendingChange durable store 和 inference gate安排到 L2，因此“L1 所有 inference 必须 pending”不是现设计的必要条件，也不应由本评审强行扩大 scope。

Hermes 提供两种可借鉴能力。其 `/journey` 可以 edit/delete memory，见 memory 文档 `:213-229`；`memory.write_approval:true` 可以让 background write staging，但该开关默认 false，见 `:258-283`。这说明审批应是策略选择，纠错和可见来源则是上线后的基本恢复能力。

**修正。** Conservative L1 至少提供 memory list/show/correct/remove，并展示来源 attempt/evidence；correct/remove 走 exact ID + expected digest，更新后下一 snapshot 原子替换旧内容。是否把 inference 默认 pending 应由 P5 quality 结果和 rollout config 决定；不要把可选审批写成 Hermes 默认或 DSH 唯一安全方案。

**验收。** `memory-show-resolves-source-attempt`、`memory-correction-uses-id-and-digest`、`memory-correction-removes-old-content-from-next-snapshot`、`memory-remove-is-user-governance-only`、`optional-memory-approval-does-not-change-default-without-config`。

### 11. S1：scanner 上限与可见内容上限没有配置不变式

**证据。** `packages/util/content-scan/src/index.ts:1-13,68-82` 明确 scanner 是 advisory guard，只扫描前 65,536 字符，并不承诺完整安全；测试 `content-scan.spec.ts:96-105` 钉住后缀不扫描。问题不在于文档隐瞒，而在于 P1 `maxEntryChars`、P2 `maxFileBytes` 是独立 Config，没有要求它们不超过 `MAX_SCAN_CHARS`。如果配置允许更长内容，blocked pattern 可以位于永不检查的后缀。

**修正。** 首版最简单的闭合是 load-time 校验 `maxEntryChars <= MAX_SCAN_CHARS`、`maxFileBytes <= MAX_SCAN_CHARS`，并对 frontmatter 中所有模型可见字段计入同一文件扫描。若业务确实需要更大文件，再实现完整扫描；对任意 regex 做 chunk overlap 不能凭固定 overlap 自动证明完整，因此不应把“分块扫描”写成无条件正确答案。README 继续声明 pattern guard 的已知绕过，不把无 findings 称为可信内容。

**验收。** `memory-entry-limit-above-scan-cap-fails-load`、`skill-file-limit-above-scan-cap-fails-load`、`attack-at-last-allowed-character-is-scanned`、`every-model-visible-skill-field-is-within-scanned-file`。

### 12. S1：curator 的活动信号和 archive→revive 路径不一致

**证据。** P4 `:38-47` 把成功 managed `skill` tool load 记为 modelLoads/lastMeaningfulUseAt，而 `/name` user load 不进入 stale 锚点；usage observer 是 live best-effort，丢失“只影响 curator 质量”。P2 provider 只暴露 active|stale，隐藏 archived；P4 phase exit `:64` 却要求“归档→复活→active”端到端。archived skill 不能被模型 load，因此无法由该信号自动复活。

**验收。** `explicit-user-invocation-refreshes-activity`、`model-load-is-not-verified-success`、`observer-gap-defers-inactivity-transition`、`stale-model-load-reactivates`、`archived-skill-requires-governance-restore`、`restore-makes-skill-visible`。

### 13. S1：P5 方向正确，但还不是可执行升级门

### 14. S2：provenance 数据存在，但反向查询与展示未冻结

## 五、建议的修订架构与阶段顺序

```text
实时 root session ─┐
                  ├─> ReviewScheduler / HistoricalReviewCoordinator
冷历史 root session ┘                 │ durable claim + retry/rate policy
                                     v
                     LearningView + OutcomeEvidence
                                     │ explicit review input
                                     v
                         tool-free ReviewPlanner
                                     │ immutable ReviewPlan
                                     v
                enumeratePlanOps + canonicalPlanOpDigest
                                     │ Host operation ids
                                     v
             exact-target + whole-plan admission + stored plan
                         │                       │
                         ├─ MemoryService        └─ ManagedSkillService
                         │                           draft/pending
                         v
             memory correction/governance ← user → skill governance
                         │                       │
                         └──── approved/visible state ────┐
                                                         v
                                           scan + digest + publication
```

P1 可以继续实现 Service、Publisher 和装配；不需要等待 P3 production canonicalizer，因为 P1 接受 HostMemoryOp 即可。P1 出口前必须增加 publication-budget closure，并把 `maxEntryChars <= MAX_SCAN_CHARS` 作为 Config 验证。

P2 在 Store/Provider/structure 纯函数层可以继续，但 create/patch mutation path 在 DirectToolOperationOrigin 与 receipt owner 冻结前不能完成。`skill_manage` 的 tool context 已提供 callId/agent，不需要向模型 schema 添加 ID。

P3 先补 production `enumeratePlanOps/canonicalPlanOpDigest`、root-only/tool-free planner、exact memory target 和 OutcomeEvidence，再做 saga。Finalization REAL boot 必须增加 after-finalized crash；retry 需要真正的 durable due gate。历史 coordinator 可以作为独立批次；若推迟，产品文档同步缩小“历史会话”承诺。

P4 将 active↔stale 与 archived restore 分开。best-effort observer 缺失时只延后归档，不把缺失解释成零使用。用户显式 skill invocation 应进入 activity。

P5 不必改名或前移；它本来就是 rollout gate。需要新增可执行 fixture、阈值、失败动作和 shadow proposal revalidation，使“人工升级 gate”成为可复现的验收而不是一句原则。

## 六、应补充的函数规格

#### `deriveDirectToolOpId(sessionId, callId, canonicalArguments): OpId`

由 `skill_manage` Host exec 构造；模型 schema 不含该字段。相同 durable call 重放得到同一 ID，不同 session 即使 provider 重用 call id 也不碰撞。

#### `enumeratePlanOps(plan): readonly EnumeratedPlanOp[]`

固定 memory/skill 数组的跨资源顺序和 stable index；stored plan 恢复永远使用同一枚举。禁止依赖对象属性枚举或 commit 成功顺序。

#### `canonicalPlanOpDigest(op, identityVersion): string`

只编码 ReviewPlan op 的 schema 字段；固定 key、undefined、Unicode、数组和版本语义。P1 的 Host op result digest 不参与该函数。

#### `resolveMemoryPlanTargets(plan, state): ResolvedPlan | Rejection`

update/remove 以 entry id + expected digest 精确解析；unknown、stale、重复目标返回结构化 whole-plan rejection。

#### `classifyOutcome(events, range): readonly OutcomeEvidence[]`

从 durable event 和 Host 可观察结果生成成功、失败→修复→成功、用户纠正、unresolved、transient 与 unknown；assistant 文本不能单独制造 verified success。

#### `claimDueRange(sessionId, desiredThrough, now): ClaimResult`

在一个明确 owner 中检查 cursor、latest disposition、blockedUntil、attempt cap 和 manual hold。函数名可以不同，但 due 判断不能只停留在 runtime prose。

#### `reconcileReviewState(sessionId): ReconcileReport`

先完成 unfinalized terminal obligations，再清理 finalized+occupied cursor；reconciliation 完成前不接受新 mutation。

#### `enumerateHistoricalReviewWork(query, checkpoint): AsyncIterable<WorkItem>`

稳定枚举授权 root sessions，durable checkpoint，支持速率、token、取消和 opt-out；实时/历史 worker 共用 per-session claim。

#### `resolveLearningProvenance(opId): AttemptEvidenceRef | undefined`

由 ReviewLedger 查询或索引，不从 hash 反推，不依赖 receipt ring；供 memory/skill 治理 show 和质量评估使用。

## 八、放行判断

P1 批 C：**有条件继续。** 现有 memory pure layer 无需因已撤回的 OpId 自引用判断返工。完成前补 publication budget closure、scanner/config 上限关系，并避免把 Host result digest 当成未来 plan digest。

P2：Store/Provider/structure 可以继续，create/patch mutation path **暂缓放行**，直到前台 ToolCall-derived OpId 与 receipt owner 明确。

P3：**暂缓放行 planner 与 finalization commit path。** 必须先补 tool-free/root-only、exact memory target、OutcomeEvidence、canonical plan owner、durable retry gate 和 after-finalized recovery。

P4：**按修订状态机后放行。** stale 可由真实活动恢复；archived 只由显式 restore；observer coverage 不完整时不得根据“零事件”归档。

Conservative L1：**必须通过现有 P5 方向所要求的可执行质量门。** unresolved failure 进入可见知识的数量必须为零；纠正后的旧 memory 不再发布；重复任务结果不得低于 no-learning baseline；shadow proposal 不得直接升级为可见状态。

L2：在 user scope 启用前冻结 principal identity；如果部署只支持一 OS profile 一用户，明确写成限制。跨 LLM provider review 不属于当前 RC5.5 缺陷，未来新增该配置时再单独评审数据披露政策。

**最终判断：保留主架构，修正协议后分阶段继续，不支持按现稿直接完成 P2/P3。** 本轮复核撤回了证据不足的严重结论，也缩减了过度设计的 requestDigest、全量 provenance 复制和 L1 强制审批建议；剩余问题均能从当前两仓源码或 RC5.5 内部矛盾直接定位。修订目标仍是：只有可精确定位、由结果证据支持、可纠正且可恢复的学习，才能进入未来模型上下文。
